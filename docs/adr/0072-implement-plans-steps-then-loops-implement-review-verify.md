# `/implement` plans Steps, then loops implement, review, and verify

`/implement` starts with a **Planner** that walks the code and slices the Spec into **Steps**, each small enough for one fresh agent, and commits them as Step files. About half of Specs are one Step. Then it runs one loop over the whole Spec: an **Implementer** per Step builds the change, `/code-review` judges it on the Standards axis alone — the repo's Coding standards and the **Design principles** — and a **Verifier** checks it does what the Spec asks, by reading the Spec against the diff, running the build and the whole test suite, and running the Spec's **Hand checks**. A **Hard violation** from Review, or a Verify finding, sends the run back to a single fresh Implementer with those findings, for at most three **Iterations**; the third that still fails halts the run. A **Judgement call** sends the run nowhere: it waits for the next Implementer when another Iteration runs anyway, and otherwise lands unfixed and is listed in the final report. From the second Iteration on, Review reads only that Iteration's fix, with the findings it was meant to fix. The run lands when one Iteration passes both.

`/to-spec` and `/grill-with-docs` aim for Specs one agent can build, but nothing guarantees it, and a Spec too large for one context fails late and expensively. The Planner is cheap on a small Spec, one walk whose Footprint the Implementer then starts from instead of walking again, and on a large one it is what keeps each Implementer inside one context.

The loop closes: every fix is reviewed and verified again before the run lands, so no Hard violation or Verify finding lands unchecked. A Judgement call is an opinion about the shape of correct code, and a fresh reviewer on the whole diff always has another, so a loop on every finding never settles. Reviewing only the fix, against the findings it answers, gives each later Review something to finish. Review lives in one place and verification in one place, each with one agent and one report, so there is nothing for several agents to keep in step.

Review judges how the code is written; Verify judges whether it does what was asked. Keeping them in separate agents stops one from masking the other, the same reason `/code-review` keeps its two axes apart. Review runs first because a Standards fix can change behaviour, and the Verifier should run on the code that would land.

## Considered Options

- **No Planner: one Implementer builds the whole Spec.** Tried, then reversed. It relied on every Spec fitting one agent's context, and a Spec that did not halted only after an Iteration's worth of cost.
- **A size target for Steps, judged from the Step file.** Rejected: nothing the Planner can see before code exists predicts which Step grows. Of 692 Step-building Implementers from 2026-10-16 to 2026-10-29, 90 passed 200k tokens of context, and their turns above 200k took 24% of builder cost. The best stand-in, a Footprint of 11 or more files, flagged 44 of those 90 and 145 Steps that stayed under. Acceptance-criteria count and Step-file length did worse. A second count, of 652 builders from 2026-10-30 to 2026-11-07, agrees: turns above 200k took 25% of builder cost, and of the 518 Steps matched to a Step file, 79 passed 200k and a Footprint of 11 or more files flagged 31 Steps for 9 of them. Only 2 of 206 one-Step runs passed 200k, peaking at 232k.
- **A long Step handed to a fresh Implementer mid-Step.** Rejected: after about 50 turns the Implementer would commit what it has and write a partial Outcome, and a fresh one would continue the Step. On the same logs it saves roughly $120 in 13 days, about 10% of builder cost and 5% of implement spend. It costs a new run state, commits of half-built Steps that may not compile, and agents that count their own turns only roughly. No Implementer reported a Step as too big. Host compaction gives the same reset without any of those costs.
- **A limit on turns that stops the Implementer.** Rejected: a stop turns a large Step into a failed one, and the run pays for a retry.
- **Flag an oversized Spec before the run.** Rejected: of 302 runs from 2026-10-30, 49 had an Implementer above 200k, and the best signal a Spec shows, 16,000 characters or more, flagged 83 runs for 42 of them. Step count predicts better but exists only after the Planner, and run cost is about $3 to $4 per Step from three Steps up, so a split alone does not clearly save anything.
- **Review and Verify each Step.** Rejected: a Step is not a change anyone ships, the per-Step reviews and verifications multiply the cost of a large Spec, and the Spec's Hand checks describe the whole change. Review and Verify judge all Steps together, once per Iteration.
- **Steps on every Iteration, fixing findings Step by Step.** Rejected: findings land across Steps, and one Iteration's fixes fit one agent.
- **A `Depends on:` line naming which earlier Outcomes a Step reads.** Rejected: an Outcome is a few lines, so every Step reads all earlier ones, and nothing can be left off by mistake.
- **Keep the Proof ladder and Safety fact inside Verify.** Rejected: the Spec's Hand checks and the whole suite already say what must hold, and a Safety fact per change was a second spec the agents wrote for themselves. A Hand check on a running surface drives the app through the repo's Verify skill ([ADR-0075](0075-setup-verify-writes-the-verify-skill-the-verifier-drives.md)).
- **Run Verify even when Review found a Hard violation.** Rejected: the Implementer's fixes would change the code Verify just checked, so the next Iteration's Verify repeats the work.
- **Review and Verify in one agent.** Rejected: one context then judges both, and a strong finding on one axis crowds out the other.
- **A Fixer after Review, separate from the Implementer.** Rejected: a fresh Implementer each Iteration is that Fixer, under the same contract, so one agent file covers both.
- **Any Review finding loops.** Tried, then reversed. In a benchmark smoke pass, Review findings drove a one-Step bug fix through three Iterations, 15 minutes and $4.40 against 9 minutes and $2.84 before the loop, with the Opus reviewer $1.03 of the gap; a six-file Spec halted after three Iterations of Review findings without Verify ever running. Each extra Iteration paid a fresh Implementer's orientation and a fresh Opus review for any finding, however small, though `/code-review` called every principle finding a judgement call.
- **A Hard violation raised whatever the Spec says.** Tried, then reversed. In two `mvdmio-suite` runs the Review raised the flagged code again after the Implementer declined it for a Spec decision, as [ADR-0026](0026-implement-agents-close-leftover-gaps.md) tells it to: one run spent an extra Iteration, and the other stopped to ask a person.
- **Every Review reads the whole diff.** Rejected: a fresh reviewer on the whole change raises new judgement calls each time, and the cost of the Review grows with the change rather than with the fix.
- **One Implementer fixes the Judgement calls before Verify, with no Review after.** Rejected: it adds an Implementer to most runs, and a fix that rides an Iteration the run needs anyway costs nothing extra.
- **Resume from a Halt record as Iteration 2.** Rejected: it needs no exceptions to Iteration 1, but it gives that resume one Iteration fewer than any other, and a resume is a fresh run with more to start from.
- **Resume only after a halt on Verify findings.** Rejected: a Hard violation halt pays for the same whole-diff Review before its known findings reach an Implementer, and the skill would need a rule to tell the two apart.
- **Resume by running Verify alone to find the findings again.** Rejected: it still pays for a full Verify, it cannot recover a Hard violation, and it loses the Judgement calls and declines.
- **Resume by asking the user to paste the halt report.** Rejected: the user has to keep the report, and it holds no declines.
- **Ignore the Halt record once anyone commits after it.** Rejected: a person who fixes one finding by hand would pay for the whole-diff Review again and lose the Judgement calls and declines.
- **No limit on Iterations.** Rejected: a Review finding the Implementer keeps declining, or a test it cannot fix, would loop forever. Three leaves room for a fix and a fix of the fix.

## Consequences

- The Planner commits the Step files as `plan: <slug>` before any code, and each Step's Implementer commits its Outcome and `Status: done` with its code, so a resume starts at the first Step not done, or at Review when every Step is.
- A Step's Footprint is a guess. Where the code disagrees, the code wins, and the drift goes in that Step's Outcome, which every later Step reads.
- The Implementer writes to the Coding standards rules and Design principles that bear on its Step, which the Planner copies into its Step file, since the Review judges by them ([ADR-0080](0080-the-planner-copies-each-steps-rules-into-its-step-file.md)). It may decline a Review finding with a reason, and the next Review raises it again only when that reason does not hold. It fixes every Verify finding.
- `/code-review` opens each Standards finding with `Hard violation:` or `Judgement call:`. A principle finding is a Hard violation only when it names a wrong result, a crash, or lost data, and a break of a Coding standards rule marked `[judgement]` is a Judgement call ([ADR-0079](0079-a-coding-standards-rule-is-hard-unless-marked-judgement.md)). Review reads the Spec's Implementation Decisions, and a finding one of them explicitly mandates is reported as a Judgement call naming the decision, so a Spec the Implementer follows does not cost an Iteration.
- Only agents read an implement run's Review report, so its reviewer skips the `/technical-writing` bar.
- Judgement calls alone never halt a run.
- The whole test suite runs once per Iteration that reaches Verify, in the Verifier. Each Implementer builds the projects on its Footprint and runs only the tests closest to its change.
- A rebase at land that brings in code the last Verify did not check sends the run through one more Verify, and a failure there starts the next Iteration.
- A resume starts again at Iteration 1, with three Iterations, on top of the branch's commits. It is a fresh run from a further-along point.
- A halt with findings commits a **Halt record** to the run folder: the third Iteration's Hard violations or Verify findings, or those of the Verify after the land's rebase, with the Judgement calls held, the declines, and the deviations. Nothing else outlives the halted session. A resume from it makes Iteration 1 a fixing Iteration: one Implementer fixes the findings, Review reads everything since that commit, and Verify runs in full. A resumed Hard violation halt gets no fresh Review of the whole change, because the run's first Review read it.
- Commits made after the Halt record count as progress. Review reads them, and the Implementer declines a finding they already answer, so a stale Halt record needs no check of its own.
- The landing commit's body lists each Step's title when the run had more than one ([ADR-0062](0062-an-implement-run-lands-as-one-commit.md)).
- A Spec that holds several changes is still a Spec to split, because the run lands it as one ([ADR-0073](0073-a-spec-is-held-to-the-planning-principles.md)).
- Merge risk is no longer recorded during the run. `/pr` works it out from the diff when it writes a description.
- The host compacts an Implementer's context once it nears the window its agent file sets, so a long Step goes on from a summary instead of paying to re-read old tool output on every turn. Nothing stops, and the run sees no new state. The window is 200,000 because the host fires below it: a window of 100,000 fired at about 73k.
- After a compaction the host restores the current Step file into the Implementer's context, and that counts as long as the copy matches the file on disk at that moment. The agent file carries no rule to read it again: six prose rules never made an Implementer call Read, and the restored copy already puts the rules the Planner copied word for word back in front of it, which the summary paraphrases. Hand check 2 compares the restored copy with the file on disk. A finding a fixing Implementer's summary drops needs no guard, because the next Review or Verify raises it again.
- The Planner, the Implementer, and the Verifier are Spec-bound and pinned to Sonnet at `effort: high` ([ADR-0049](0049-agents-are-pinned-in-their-agent-files.md)).
