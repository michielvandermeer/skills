# Decide whether skills name the Skill tool when they load another skill

Category: enhancement
Status: needs-grilling

## Problem

Our skills load each other with a bare command in prose: "Run `/to-spec`", "Run `/plain-language`". Upstream v1.3.0 (mattpocock/skills #878, #880) changed every such step to "Call the Skill tool with `to-spec`". Upstream's reason: a skill named only in prose does not reliably load, and that was the root of its most-reported `grill-with-docs` problem. Naming the tool raises the hit rate. Dropping the `/` also avoids assuming one host's command syntax.

Upstream pairs the change with a carve-out: the Skill tool form applies only to model-invoked skills. A step that needs a user-invoked skill tells the user to run it.

This plugin runs on Claude Code and Grok, so whatever wording we choose must work on both.

## Out of scope

- Steps that need a user-invoked skill. Only `diagnosing-bugs` had one, and it now tells the user to run it.
- Prose that lists skills for a person to pick from, such as the README.

## Open questions

- Have we seen a skill named with "Run `/x`" fail to load? If not, is upstream's evidence enough to change every skill?
- If we switch: is "Call the Skill tool with `x`" the wording, or something that does not name a Claude Code tool?
- Does the rule belong in an ADR, in `writing-for-agents`, or in both?
