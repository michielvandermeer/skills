# Decide whether the slicing rules need a Step size target

Category: enhancement
Status: needs-grilling

## Problem

In 48 hours of `/implement` transcripts (2026-09-24 to 2026-09-26), Step agents ran 100–175 turns and grew to 350–590k tokens of context. Turns above 200k context took 54% of Step agent spend. The slicing rules in `skills/implement/STEPS.md` say only that a Step "fits in a single fresh context window", which the 1M window stretches a long way.

Slicing Steps smaller would keep each one under about 200k tokens. But each extra Step pays setup: about 34k tokens of fixed baseline, plus the Spec and the Outcomes it reads. The Planner cannot count tokens before any code exists, so a size rule would use a stand-in, such as how many files a Footprint lists.

A grilling session on 2026-09-26 locked this: no size target goes into the slicing rules until the measurement from commit `5d4d45e` is re-run after the Specs `implement-agents-read-in-batches` and `implement-agents-start-smaller` land. Both landed on 2026-09-26 (`178b1e2`, `43f5c27`).

## Out of scope

- The Checker, the split final fixers, and the `Depends on:` line. They landed with `implement-agents-start-smaller`.

## Open questions

- Does a smaller Step save more than its extra setup costs?
- Which stand-in can the Planner judge before code exists: files in the Footprint, acceptance criteria, something else?
- Is the post-landing sample big enough to decide on, or should the decision wait for more runs?
