### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

Redact every secret before you show it: API keys, tokens, passwords, cookies, session IDs, connection strings, and signed URLs become `<REDACTED>`. Build loops on environment variables (`curl -H "Authorization: Bearer $API_TOKEN" …`), so a credential stays out of the files you write and the output you quote. From a captured artifact (HAR file, log dump, request payload), quote only the lines that carry the signal. When the redacted output is not enough to diagnose, say so and ask.

1. Reproduce it yourself on the matching surface via the driver skill (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. The reproduction is a **tight** loop that goes **red** on this bug: one command you have already run, which drives the bug's code path, asserts the user's exact symptom, gives the same verdict every run, and finishes in seconds. Build it from **Loops** in this playbook. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. Then minimise: cut inputs, callers, config, and steps one at a time, rerunning the loop after each cut, until removing anything left turns it green. No red loop, no hypothesis.
2. Binary-search the cause. Form 3–5 ranked candidate hypotheses, each falsifiable by a stated prediction ("if X is the cause, changing Y makes the bug disappear"), then rule them out until one survives. Seed them with `how` over the affected subsystem, the area's `CONTEXT.md` and ADRs, and the **why** skill for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. Each probe tests one prediction and changes one variable. When program state is unclear, prefer a debugger or REPL, else log at the boundaries that separate hypotheses, every line tagged with one prefix such as `[DEBUG-a4f2]`, and read it as the code runs. Don't guess. When every hypothesis is disproved, or two fixes for one failing check have failed, write the one sentence they all assumed and test it before a new list. Drive a long or stubborn hunt with Claude Code's `loop` skill. Confirm the surviving *mechanism* with runtime evidence before the step-3 architect/interrogate fan-out.
3. Plan the fix. If it crosses a function boundary, `architect` first. Delegate implementation to a subagent using your configured bug-fix model (default in poteto-mode's Models section) with a specific scope.
4. Verify on the same surface. The original repro, before you minimised it, now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.
5. Stage the commits so the failing repro lands before the fix in git history. When the bug has a cheap local test path at a seam that exercises the bug as it happens at its call site, turn the minimised repro into the failing test first. Skip the test when it would be expensive, integration-heavy, or unclear. When only a shallower seam exists, skip it too and report the missing seam as a finding.
   This is the canonical [sequence-verifiable-units](../principles/sequence-verifiable-units.md) principle, the failing test first and the fix on top.
6. Clean up. `grep` the debug prefix down to zero hits and delete throwaway harnesses. State the hypothesis that held in the commit message. Then ask what would have prevented the bug. When the answer is architectural (no seam for the test, tangled callers, hidden coupling), name the structural change in your report, with the specifics.
7. Run **Opening a PR**.

**Loops**, roughly cheapest first: a failing test at the seam that reaches the bug; a curl script against a running dev server; a CLI run on a fixture input, diffed against a known-good snapshot; a headless browser script asserting on DOM, console, or network; a captured request, payload, or event log replayed through the code path; a throwaway harness of one service with mocked dependencies; a fuzz loop over many random inputs; a `git bisect run` harness between a good and a bad state; the same input through the old and the new version, diffed. Last resort, when a person must click: drive them with poteto-mode's `scripts/hitl-loop.template.sh`, so the loop stays structured. Then tighten it: cache setup, narrow its scope, assert the specific symptom rather than "didn't crash", pin time, seed randomness, freeze the network. A flaky bug needs a higher reproduction rate, not a clean repro: loop the trigger 100×, parallelise, add stress, and narrow timing windows until the rate is debuggable. When no loop can be built, stop, list what you tried, and ask for access to an environment that reproduces it, a redacted captured artifact, or permission to add temporary instrumentation.

**Reply:** what was broken, root cause, fix, how you verified. Quote the decisive failing and passing output, trimmed to the assertion and the counts.
